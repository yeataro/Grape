## Q-001 — 接線預檢能力的可組合性與責任邊界

- 記錄日期：2026-10-03。
- 來源：Human Owner 與 Coordinator 的架構討論；Human Owner 授權保存此筆記。
- 狀態：待嚴格核對。已有局部契約與程式碼閱讀，沒有完成整體能力驗證或 Fresh Independent Review。
- 本次閱讀基準：`04834e2d0c11656f9d06a3e9ab82350f6edede33`；後續查證需重新核對版本。
- 檢視時機：核對接線／型別推導核心能力時，或相關能力具備可測入口時。本條目本身不構成 S03 阻擋條件或未來工作的排程。

### 要回答的問題

模型能否承載可重用的接線合法性判定，讓不同工具自行組合候選收集、判定與呈現，而不在各處重寫規則？目前關心的是能力與責任分界；尚未選定全畫面提示、hover 提示或其他特定互動方式。

### 討論中的組合方式

1. 候選可以來自模型查詢，也可以來自視圖範圍查詢。「範圍內的節點」與「範圍內的接孔」是不同查詢；節點清單還可以展開成接孔清單。
2. 接線工具取得固定端點與候選端點後，使用共用的模型側能力判斷各候選是否合法。判定不應依賴候選清單的視覺來源。
3. 視圖決定哪些結果參與顯示。沒有整批提示時，hover 命中的單一目標也可以使用相同判定能力。
4. 是否提供原生批次查詢，或由呼叫者組合單次查詢，尚未決定。候選目標接受清單，不等於固定端點也必須接受清單，更不等於同時建立多條線的交易。

以上是待檢查的組合構想，不是新增 API 契約。

### 已核對的依據與限制

- [接線契約](../handoff/executable-reference/CORE_API_CONTRACTS.md) §2.4 區分 `check` 與正式接線；正式提交必須重驗，替換失敗保留原線。這不能直接證明 production 已有完整、共用的預檢入口。
- [動態接口契約](../handoff/executable-reference/COMPUTE_QUALIFICATION_CONTRACTS.md) §5 描述 infer 模組在候選副本中讀取來源型別與依賴順序重算。[能力盤點](../handoff/compatibility/capabilities.json) LC-NODE-376 記錄新增線須檢查完整下游與新增錯誤；不能僅比較目前顯示的兩個型別。
- [核心 API 契約](../handoff/executable-reference/CORE_API_CONTRACTS.md) §7.3 描述模型節點／Port 查詢及 CanvasView 相機狀態分離；[架構規格](../handoff/02_ARCHITECTURE_SPEC.md) §1 說明 Graph 不依賴 UI。這不代表已有現成的「可見接孔清單」API。
- 目前 [Canvas](../production/src/features/canvas.ts) 的拖線 `pointermove` 未執行目標合法性預檢，放線時才尋找目標並發送接線命令。這是上述版本的局部靜態觀察，不能據此宣告整個模型支持或不支持所有構想，也不是本筆記提出的 S03 修復要求。

### 待驗證條件

- **入口與權威：**是否有可供不同工具共用的判定入口？節點簽名、型別適配、Graph 結構與下游規則是否各有清楚來源，而非由 UI 或不同工具重複定義？
- **預檢與提交一致性：**在相同模型狀態與操作選項下，hover、候選清單與正式接線是否使用一致的語意？Auto 與下游影響是否納入？檢查不應修改正式圖或 History，提交仍需重驗。
- **候選獨立性：**一份清單的每個目標是否代表各自獨立的假設？檢查 A 不應污染 B；各自合法也不代表多條線同時提交合法。若檢查跨越模型變更，舊結果如何失效？
- **視圖邊界：**可見、可命中、模型存在、接線合法是否被分別處理？畫面外仍存在的下游約束不能只因未顯示而被忽略。
- **能力與交付狀態：**哪些已有契約與實作，哪些只是架構可以承載，哪些還缺接口或驗證？缺少特定 UI 功能不能直接當作模型架構失敗。

## Q-002 — 巢狀 subgraph 重用的產碼與圖遍歷成本

- 記錄日期：2026-10-03。
- 來源：Human Owner 與 Technical Product Steward / PM 的討論；Human Owner 授權整理到 Note，刪除或標記不成立的要求與推論。
- 狀態：有 Legacy 實際使用情境支持的待驗證問題。以下區分使用者轉述、接受契約、程式靜態觀察與分析；不是新產品效能回歸報告。
- 本次閱讀基準：工作分支 `04834e2d0c11656f9d06a3e9ab82350f6edede33`；接受架構仍為 IH-005。S03 尚待 Human acceptance，程式觀察不等於已接受的產品能力。
- 範圍：GLSL 原始碼產生、圖遍歷、接線判定與 subgraph 重複分析。GPU shader 編譯快取及預覽圖片更新不在本條目範圍。

### 要回答的問題

複雜功能反覆封裝成 subgraph，並在圖中引用多次時，哪些內部分析與產碼成果可以重用？接線操作是否會重新深入未變動的子圖，讓使用者承擔與當次操作無關的重複工作？

需要分開評估「接線判定／型別推導」與「GLSL 產碼」；Exporter 內的重用不會自動改善接線檢查。主圖畫面上的節點數也不足以代表負載，還需看子圖定義大小、巢狀深度、引用次數及各階段實際處理次數。

### Legacy 使用經驗與證據限制

- **Human Owner 的實際經驗：**複雜功能會持續封裝成子圖，同一子圖在圖內至少被引用兩三次；這已在自己的創作中發生，不只是對極端大圖的假設。
- **Human Owner 對既有分析的轉述：**效能疑慮來自 Legacy 的 lag 分析，並涉及接線時的 Auto 型別推導與傳播。本次沒有重新取得或重跑該分析的原始量測，不能宣稱已證實哪一項佔主要時間，也不能給出新舊效能倍數。
- **Human Owner 對歷史實作的轉述：**原本希望 subgraph 函式化，實作時因「常量無法傳遞」的理由而未完成。這不是 Owner 決定永久放棄函式化的證據；當時 Legacy 的精確產碼策略與命名規則仍待原始碼核對。
- **重要更正：**以上實際負載與 lag 經驗全部來自 Legacy。Owner 所說的新產品「還沒有能力被使用」，指它尚未達到能實際完成這類作品、驗證此負載的階段，不是宣告新架構不支持 subgraph 或完全沒有相關程式。

### 接受契約與目前程式各自能證明什麼

1. **模型保留子圖邊界。** [產品模型](../handoff/01_PRODUCT_MODEL.md)的 SubgraphDefinition 是 Graph 內可重用的接口與 Network，call Node 引用它。定義在主 Network 外保存，不強制產碼採普通函式，也不代表模型已按每個引用攤平。
2. **產碼與排程已有責任分界。** [架構規格](../handoff/02_ARCHITECTURE_SPEC.md) §5 與 [責任表](../handoff/03_RESPONSIBILITY_AND_DEPENDENCY.md)允許 Generator 持有本次工作的中間結果，Updates 負責 Graph-scoped、每 profile 的排程與產碼成果快取。一次性 Exporter 可以在同次匯出內重用成果；跨不同次匯出的快取是另一個生命週期。這裡的成果是 GLSL 原始碼，不是 GPU 編譯快取。
3. **目前產碼已有局部重用，但仍逐引用展開子圖。** [compiler.ts](../production/src/generation/compiler.ts) 的 `lowerNetwork` 從輸出邊界往上游產碼，`emitted` 在同一次 Network 展開中避免重複產碼；`emitNetwork` 對每個子圖使用位置重新呼叫 `lowerNetwork`，尚未共用整份定義的產碼模板。這是靜態路徑觀察，不是耗時量測。
4. **目前接線提交包含全圖驗證及重複深入子圖的路徑。** [editor.ts](../production/src/application/editor.ts) 的 connect 命令走 `Graph.change`；[graph.ts](../production/src/model/graph.ts) 隨後執行 `validate`。其中 caller 與 resource 的 stage 適用性會呼叫 [definitionStages](../production/src/sdk/networks.ts)，該函式遞迴處理子圖引用，只有遞迴路徑防循環，沒有已完成結果的重用。這是 shader stage 適用性檢查，不能冒稱已實作或重現 Legacy Auto 推導；也未證明拖線每次 pointermove 都走這條路徑。
5. **重名已有處理方式。** 同一產碼器以工作內流水號區分巢狀符號，另保留使用路徑作 provenance。接受契約也要求使用者名稱／位置不作 shader symbol 身分；「subgraph 顯示名＋節點顯示名」不能單獨保證同名定義或重複引用不衝突。
6. **全圖正確性與常量語意仍要保留。** [架構規格](../handoff/02_ARCHITECTURE_SPEC.md) §5 要求全圖 model Error 在剪枝前阻止生成，cache 命中也不能繞過當前全圖驗證。[常量契約](../handoff/executable-reference/COMPUTE_QUALIFICATION_CONTRACTS.md) §6 要求 `requireConstant` 查驗真正的 GLSL constant expression 資格。不能只依型別相同、數值固定或內部的 `constant` 標記宣稱語言層面合法。

### 已排除或附條件的推論

下表包含討論語句被擴大後才會出現的強主張，不是逐字引述，也不表示 Owner 曾正式提出這些要求。處理針對主張本身，包括 PM 先前的推論；不把使用者合理的重用需求刪除，也不撤銷既有 Human 決議。「排除」表示不再把該推論當成調查前提，不是替 Human 新增產品非目標。

| 主張 | 處理 | 理由與保留的範圍 |
|---|---|---|
| Legacy 已卡頓，因此新產品已有相同效能回歸，或新產品完全沒有此能力。 | 排除，來源混淆 | 新產品目前缺少這類實際使用證據；靜態程式觀察另列。 |
| 所有 subgraph 一律轉成普通 GLSL 函式，仍無條件保留編譯期常量資格。 | 排除，技術上不成立 | 自訂函式呼叫結果不能形成 GLSL constant expression；固定數值仍可正常當作函式參數傳入。需要常量資格的路徑必須另行處理。 |
| 常量有限制，所以必須永遠放棄函式化，而且每次都重新分析整份子圖。 | 排除，推論過度 | 常量限制只否定無條件的普通函式替換，不否定其他路徑函式化、同次匯出重用分析或模板。 |
| Exporter 是一次性的，因此不能重用子圖成果。 | 排除，生命週期混淆 | 本次匯出可建立工作內暫存，完成後釋放；不必先引入跨次快取。 |
| subgraph 名加節點名就能保證不重名。 | 排除，條件不足 | 同名定義、同一份定義多次引用及巢狀引用仍會碰撞；需要區分使用位置或使用可靠的符號配置。 |
| 函式化，或撤回接線 Auto，單獨就能消除接線成本。 | 排除，未建立因果 | 函式化主要影響產碼；撤回 Auto 不會自動移除其他全圖檢查、引用遞迴或查找成本。本條目不決定 Auto 的去留。 |
| 全圖正確性要求等於必須按每個引用重新做全部內部分析。 | 不採為必然前提 | 可調查安全的結果重用，但必須完整保留依賴失效與當前錯誤判定，不能省略未達輸出節點的驗證要求。 |
| 外露 Port 型別固定，所以接線只看兩個 Port 即可保證整圖合法。 | 附條件，不能當作完整合法性結論 | 型別邊界有助於限制型別分析；循環、常量來源、stage 適用性、資源依賴及當前錯誤仍各有規則。Edge 的兩端責任不等於 Graph 沒有其他檢查。 |
| 同一份 subgraph 的完整 GLSL 可以原樣貼到所有使用位置。 | 附條件，尚未證實 | 輸入表達式、常量、資源、profile、符號及 provenance 可能不同；需界定哪些成果可共享、哪些必須按使用位置產生。 |

常量限制的外部依據：[GLSL 4.60 §4.3.3 Constant Expressions](https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.4.60.html#constant-expressions)。這裡記錄語言限制，不宣稱已完成所有 Grape profile 或 GPU 的資格驗證。

### 保留的比較方向

- **逐引用完整展開：**目前可觀察的產碼路徑；可能同時重複內部分析與 GLSL 內容，實際成本待量測。
- **同次匯出重用分析或模板，再按使用位置展開：**可能減少內部分析；仍需處理符號、常量與 provenance，輸出字碼量未必縮小。這是待驗證選項，不是已完成能力。
- **共用函式或依必要條件產生專用版本：**可能減少重複函式內容；普通函式有常量限制，專用版本又可能隨常量組合增加。尚未選定，也不要求全面改成新 IR。

上述選項都不能直接替代接線階段的依賴與合法性分析。新架構是否能承接 Legacy 負載，是本問題的調查目的；目前沒有證據要求為結構美觀重設架構。

## Q-003 — 節點的多目標與不同版本支援

- 記錄日期：2026-10-04。
- 來源：Human Owner 與 Technical Product Steward / PM 的討論；Owner 最後指示「這邊也只能先筆記」。
- 狀態：保留修訂意向，尚未形成可採用的契約修訂。PM 上一輪稱為「確定的能力要求」，本條目依 Owner 最新指示僅作工作筆記，不登記為已接受決議。
- 範圍：節點對不同宿主／產碼目標及版本的適用性、實作與資料責任；不自行加入 S04、形成驗收阻擋或授權實作。

### 保留的意向

Owner 希望「節點要有復數目標、不同版本的能力」。要探索同一種節點是否能在多個目標下使用，必要時交出不同形式的 GLSL，而不必僅因產碼差異就更換節點或經過匯出／匯入。

討論例子包括 WebGL／GLSL ES、desktop GLSL、TD TOP、TD MAT 的 vertex／pixel。這些例子包含宿主、語言版本與 stage 等不同面向，尚未決定如何分類或表示。PM 暫將「不同版本」理解為目標／語言版本，Owner 尚未明確界定；不能推定允許混用節點定義版本或解除 exact pin。

### 尚未決定

- 支援宣告放在節點定義、Module、Profile 或其他資料中；是否擴充節點表，以及如何沿用現有 eligibility／capability 契約。
- 誰負責選擇對應實作，誰負責新增節點篩選、圖驗證與產碼的支援判定。
- 同一節點用一份或多份實作；跨目標是否共用 state、參數與接口，以及相同行為需要維持到什麼程度。
- 目標專屬選項是否可以隱藏但保存，或必須拆為不同節點定義。兩種做法都曾討論，沒有定案。
- 是否要求所有節點提供 WebGL 實作，或只要求明確表示支援／不支援。Owner 提出的「pass 過去」尚未形成具體行為定義；不得直接解讀為允許跳過節點、透傳輸入或靜默降級。

### 已有契約依據與邊界

- [Extension model §2](../handoff/04_EXTENSION_MODEL.md)已有節點 graph kind／stage／generator capability 適用性、Graph 持有 state、Module 持有功能定義及純 callback 的責任。[§6](../handoff/04_EXTENSION_MODEL.md)已有 GLSLProfile 目標支援、版本及能力限制。
- 同一節點依多目標／版本選擇實作的完整規則，仍需核對現有契約覆蓋程度，不能因上述機制存在就宣告已完整承諾或實作，也不能僅因缺少直接的 target 欄位就判定必須新增架構。
- 目前契約要求不支援的操作明確診斷、阻止生成；已載入的錯誤資料可保留，不能靠隱藏替代節點假裝成功。依據為 [Extension model §2、§6](../handoff/04_EXTENSION_MODEL.md)及 [Architecture spec §5](../handoff/02_ARCHITECTURE_SPEC.md)。本筆記沒有改變這些規則。
